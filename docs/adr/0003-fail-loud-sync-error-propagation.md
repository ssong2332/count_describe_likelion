# 0003. 동기화 실패를 삼키지 않고 사용자에게 노출한다 (Fail-loud)

- 상태: 제안 (사후 기록 — 구현·배포 완료 후 작성, 사용자 승인 대기)
- 날짜: 2026-08-25
- 결정자: architect
- 관련 결정: DECISIONS.md #6
- 사용자 요청 원문 (축어 인용): "1. 오류 은폐 구조도 고쳐줘"

## 맥락

모든 Firebase 실패가 `console.warn` 및 `.catch(() => {})`로 삼켜져 있었다. 클라우드 저장이 통째로 실패해도 화면에는 아무 표시가 나지 않았고, 사용자에게는 "저장된 것처럼 보이지만 실제로는 아무것도 저장되지 않은" 상태가 남았다. 이번 장애 내내 REST 404와 WebSocket 실패가 계속 발생했으나 사용자는 알 수 없었다.

기존 Architecture.md "에러 처리" 절은 `{ success, error }` 형태의 Result 래핑을 규정했으나, 실제 코드는 그 규약을 따르지 않고 침묵했다. 이 ADR은 규약을 실제 구조에 맞춰 다시 정한다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지 (실패 무음, 콘솔만) | 화면이 절대 멈추지 않음, UI 흐름 단순 | 저장 안 된 것을 저장된 줄 안다 — 부스 실운영에서 데이터 유실로 직결. 장애 발견이 늦다 |
| B. Result 객체 반환 (`{ success, error }`) | 예외 없이 흐름 제어, 타입으로 강제 | 호출 지점 전부가 반환값을 검사해야 하며, 검사를 빠뜨리면 다시 무음이 된다 (기존과 같은 실패 양상) |
| C. 예외(SyncError)로 던지고 UI 경계에서 표시 (채택) | 검사를 빠뜨려도 침묵하지 않는다. 실패가 기본적으로 드러난다 | 실패 시 작업이 중단된다. 잡지 못한 예외가 렌더 트리를 무너뜨릴 위험 → ErrorBoundary로 상쇄 |

## 결정

C를 채택한다.

- `src/services/rest-client.ts`의 `firebaseRest()`가 네트워크 실패와 비2xx 응답을 `SyncError`로 던진다. `SyncError`는 상태코드별 한국어 안내 메시지와 `url`·`status`를 함께 싣는다 (401/403 = 권한 거부·보안 규칙 확인, 404 = 주소 없음·설정값 확인, 5xx = 서버 오류).
- 쓰기 실패 12곳이 오류를 전파하고, SDK 미러 쓰기의 무음 실패 20곳은 `console.error`로 남긴다 (인용 — 지점 수는 구현 보고 값, 이 세션에서 재계수하지 않음).
- `IRoomService.subscribeRoom(roomId, callback, onError?)`에 `SyncErrorCallback`을 추가해 구독 끊김·초기 조회 실패·DB 미초기화를 `useRoomSync`의 `error`로 전달한다.
- UI는 `AdminDashboard`에서 `error`(구독 계열)와 `actionError`(액션 계열)를 함께 배너로 표시하고 닫기 버튼으로 해제한다.
- 함께 둔 방어선: `src/components/common/ErrorBoundary.tsx`를 앱 루트에 배치해, 어떤 렌더 예외에도 빈 화면 대신 오류 메시지와 새로고침 버튼을 보인다.

## 결과 (트레이드오프 포함)

- 받아들인 대가: 클라우드 저장이 실패하면 조용히 넘어가지 않고 **작업이 중단되며 오류가 표시된다.** 저장되지 않은 것을 저장된 줄 아는 것보다 낫다고 판단했다.
- 얻는 것: 장애가 사용자·개발자 모두에게 즉시 드러난다. 메시지에 상태코드별 원인 힌트가 있어 설정 오류와 권한 오류를 구분할 수 있다.
- 감수하는 것: 일시적 네트워크 흔들림에도 배너가 뜬다. 재시도·오프라인 큐는 도입하지 않았다 (PRD에 요구 없음 — 필요해지면 별도 ADR).
- 예외적으로 삼키는 경로: 알림 발송(ADR-0004)과 `room-history` localStorage 쓰기. 둘 다 실패해도 핵심 데이터 정합성에 영향이 없고, 전파하면 렌더 트리를 무너뜨리기 때문이다. 삼키되 `console.error`는 남긴다.
