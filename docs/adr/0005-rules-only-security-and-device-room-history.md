# 0005. DB 보안은 규칙만 강화하고, 룸 목록은 서버 열거에서 기기 접속 기록으로 바꾼다

- 상태: 제안 (사후 기록 — 구현·배포 완료 후 작성, 사용자 승인 대기)
- 날짜: 2026-08-25
- 결정자: architect (선택지는 사용자가 결정)
- 관련 결정: DECISIONS.md #8
- 사용자 요청 원문 (축어 인용): "그래도 데이터베이스 관리는 해야되잖아 룸 목록 버튼을 삭제하되 다른 방안 있어?"
- 사용자 선택 원문 (축어 인용): DB 보안 방식 — "규칙만 강화 (코드 변경 없음)" / 룸 관리 대체안 — "기기 기준 룸 목록 + 콘솔 (권장)"

## 맥락

Firebase Realtime Database가 **무인증 공개** 상태였다. 누구나 `/rooms.json`을 열거해 전체 룸과 인원 정보를 읽고 쓸 수 있었다.

보안 규칙을 게시하자 `/rooms` 열거가 차단되었고(게시 후 실측 401 — 인용, 이 세션에서 재실행하지 않음), 서버 열거에 의존하던 룸 목록 기능이 동작 불가가 되었다. 사용자는 "룸 목록 버튼을 삭제하되 다른 방안"을 요구했고, 제시된 선택지 중 "기기 기준 룸 목록 + 콘솔 (권장)"을 택했다.

## 검토한 대안

### (1) DB 보안 방식

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 규칙만 강화 (코드 변경 없음) — **사용자 선택** | 즉시 적용, 코드·배포 무변경, 열거·전역 읽기 차단 | 인증이 없어 룸 코드를 아는 사람의 읽기·수정을 막지 못한다 |
| B. 익명 인증 + `auth != null` 규칙 | 실제 접근 주체 식별, IDOR 방어의 출발점 | 콘솔 설정 변경 + REST 직접 호출을 SDK 경로로 정리하는 코드 변경이 필요 |

### (2) 룸 관리 대체안 (열거 차단 이후)

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 룸 목록 버튼 삭제 | 가장 단순 | 관리자가 자기가 만든 룸 코드를 잊으면 되찾을 수단이 없다 |
| B. 기기 기준 룸 목록 + Firebase 콘솔 — **사용자 선택** | 열거 없이 목록 UX 유지, 영구 삭제·복구는 콘솔이 담당 | 기기를 바꾸면 목록이 비고, localStorage를 지우면 사라진다 |
| C. `/roomIndex` 같은 공개 인덱스 노드 유지 | 어느 기기에서나 목록 조회 | 열거 차단의 취지를 정면으로 무효화한다 (사실상 무인증 공개 복원) |

## 결정

- `firebase.rules.json`을 게시한다. 루트와 `/rooms`는 `.read/.write: false`(열거 차단), `/rooms/$roomId`만 `.read: true` / `.write: "newData.exists()"`로 열고, `roomId`·`pin`·`createdAt` 필수와 `members/$memberId`의 `name`·`activeStatus`·`isPresent` 타입·형식을 `.validate`로 검증한다. `newData.exists()` 조건이 **룸 영구 삭제(null 쓰기)를 금지**한다.
- `src/services/room-history.ts`가 이 기기의 접속 룸을 `localStorage`(`count_status_room_history`)에 **최대 10개**(`ROOM_HISTORY_LIMIT`) 기록한다. `App.tsx`의 세션 저장 시점에 `recordRoomVisit(roomId, role)`가 호출된다.
- `RoomListModal`이 `getRoomHistory()`를 목록의 원본으로 쓴다. 각 룸의 인원수는 **룸 코드를 알고 있으므로 개별 조회**(`/rooms/$roomId`)로 채운다.
- 규칙이 영구 삭제를 금지하므로 삭제 버튼은 **"이 기기 목록에서 빼기"**(`forgetRoom`)로 바뀌었다. 영구 삭제·복구는 **Firebase 콘솔**에서 사람이 수행한다.

## 결과 (트레이드오프 포함)

- 얻는 것: 전체 룸 열거·전역 읽기 차단. 스키마 검증으로 오염 쓰기 일부 차단. 코드 변경 없이 즉시 배포 가능한 보안 개선.
- 감수하는 것: 룸 목록이 기기 로컬이다 — 기기 변경·브라우저 데이터 삭제 시 목록이 비고, 룸 코드를 따로 알아야 복구된다. 영구 삭제는 앱에서 불가능하고 콘솔 작업이 된다.

## 남은 한계 (반드시 기록 — 부스 실운영 전 해소 필요)

1. **인증이 없으므로 룸 코드를 아는 사람의 읽기·수정은 막지 못한다.** 규칙은 열거만 막을 뿐 접근 주체를 식별하지 않는다.
2. 부스 실운영 전 **익명 인증 전환**이 필요하다. 전환에 드는 것: ① Firebase 콘솔에서 익명 로그인 활성화, ② 규칙을 `auth != null`로 변경, ③ 현재의 REST 직접 호출을 SDK 경로로 정리하는 코드 변경.
3. **이 전환의 핵심 제약**: 현재 구조가 REST와 SDK로 이중 쓰기를 하고 있어 **REST 경로가 인증 토큰을 싣지 않는다.** 규칙을 `auth != null`로 바꾸는 순간 REST 경로 전부가 401이 된다 — 규칙 변경과 코드 정리는 반드시 함께 배포해야 한다.
4. `.write: "newData.exists()"`는 룸 노드 삭제만 막는다. 룸 코드를 아는 제3자의 **덮어쓰기**는 막지 못한다 (1번과 같은 뿌리).
